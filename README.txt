GVS 2.4.6 — адаптивная команда в DeepSeek Harness 0.2.1-rc.2

2.4.6: User/QA сохраняет и выполняет сценарии по шагам, дополняя по ID без удаления остальных случаев. missingCategories ограничивает итоговый pass, а не начало исследования. Все реальные проверки и нужные категории обязательны при приёмке. Задания, остановленные старым планировщиком, восстанавливаются один раз с теми же ID; настоящие блокировки и человеческая пауза сохраняются.

2.4.5: браузерный инструмент публикует точные допустимые actions/states; неподдерживаемый viewport отклоняется до capture. Complete своей queued-задачи не принимает pass и возвращает фактическое ожидание, повтор завершённой задачи не меняет исходный результат. Все приёмочные gates сохраняются.

2.4.4: смена модели человеком сохраняет маршрут спящих членов команды для их следующего запроса. После успешного сохранения провайдерные blocked-задачи с реально изменившимся provider/model возвращаются в очередь с теми же ID, планами и сохранённым lastFailure. Настоящие source/QA блокировки, человеческая пауза и индивидуальные overrides не обходятся.

2.4.3: gvs_wait доступен специалисту как read-only статус, прерванный отзыв передаётся Lead без ложного завершения. Ошибки инструментов, проверок и остановившихся агентов автоматически сохраняются в gvs_diagnostics и передаются координатору; повторения требуют вмешательства. User-инструкции ограничены соответствующей ролью; редактор кода не превращается в тестировщика.

В 2.4.2 Пользователь автоматически получает реальные исследовательские UI-проверки при доступном preview и после готовых UI-инкрементов. gvs_user_testing планирует сценарии, а pass требует собственных реальных действий и assertions на desktop/phone. Окна надо открыть, закрыть и вновь открыть; ошибки сразу передаются координатору. Полная UI QA проверяет поведение независимо. gvs_visual action:states постранично возвращает все существующие обязательные кадры, в том числе без warnings, с точными ID; ошибки complete называют пропущенные кадры.

В 2.4.1 добавлен gvs_artifacts: реальные файлы результатов, без угадывания HANDOFF.md/INTEGRATION.md. Текстовые отчёты больше не требуют совпадения кодового anchor по заголовку; обещанные выходы должны существовать перед pass. Абсолютные пути проекта нормализуются, внешние тестовые пути учитываются отдельными environment leases без расширения Native прав записи.

Восстановление после прерывания сохраняет частичные правки и исходный план, проверяет последующий дрейф исходников и требует заново выполнить проверки. Ручная пауза автоматически не снимается.

В 2.4.0 координатор изучает исходники и задаёт codePlan: точные файлы/реальные anchors/изменения, команды проверки и критерии результата. Новые задачи изменения кода без плана не запускаются. Хеши источников проверяются перед назначением; исполнитель реализует план и сообщает о расхождениях. Для pass нужны реальные изменения и успешные команды на актуальных запланированных файлах. QA/User могут отклонить ошибочный план. Независимые ветки остаются параллельными; текущие legacy slices сохраняются при миграции. Пропущенный reason при update больше не ломает вызов: журналируется фактический diff полей, а одинаковый повтор ничего не меняет.

В 2.3.1 исправлен слишком низкий предел read (180 → 2000 строк при прежних 22000 байтах), добавлено восстановление финального отчёта из полного Native stdout до 8 МиБ и снят общий предел 64 браузерных проверок на весь run. gvs_ask_user action:status возвращает актуальные решения с ID, а ошибки завершения задачи объясняют точную форму запроса. Отказы доступа, неуспешные проверки и недостаточная приёмка не маскируются.

МОДЕЛИ САБАГЕНТОВ
В панели команды нажмите «Модели»: общая модель и усилие задаются для «Всей команды», личные — для выбранного агента. Кнопка модели внизу карточки открывает его личные настройки. Изменения применяются со следующего запроса без отмены текущей работы.
По умолчанию команда следует модели и усилию координатора. Личные переопределения имеют приоритет. «Сбросить на наследование» возвращает наследование. Настройки сохраняются в текущем чате после перезапуска и применяются к новым/возобновлённым агентам. Bundle автоматически включает глобальный плагин /models.

Откройте http://localhost:3080/, создайте чат в папке проекта и опишите результат. GVS добавляется к стандартным режимам Standard, PTC, Minimal и Creator. Выбирать Пользователя, дизайнера и другие внутренние роли не нужно. Для реализации нужны права записи в проект, для визуальной приёмки — модель с изображениями. Команда наследует модель основного чата. Провайдер модели и вход настраиваются в Harness; плагин не переносит учётные данные.

Команда и ожидание
Координатор читает проект и сам создаёт нужные роли: например гейм-дизайнера, дизайнера уровней, специалиста по камере, разработчика, игрового QA или проверяющего доступности. У каждой роли конкретная цель и возможности read/edit/verify. Пользователь создаётся автоматически и служит общим критичным представителем аудитории; специалисты консультируют его по UX, дизайну и логике. Эта модельная роль не заменяет человека и не выдаёт разрешения от его имени.
У каждого агента настоящий сохраняемый чат DSH Agent Teams. Новое задание подходящему агенту продолжает тот же чат. Можно создать недостающего специалиста, оставить его без работы и позднее разбудить новой задачей. Координатор принимает запросы коллег о необходимых ролях. Ограничения: до 32 сохраняемых ролей и 10000 задач за запуск.
План — настоящий граф зависимостей. Проверяющий не выполняет задачу до завершения предшественника; после разблокировки запускается автоматически. Пробуждение не создаёт дубль и не обходит зависимости. Независимые задачи могут работать параллельно: по умолчанию четыре слота, до восьми через gvs_parallel. readScopes/writeScopes/resources защищают пересекающиеся области и общие среды; старые задания без областей сохраняют консервативную очередь. Целая финальная проверка ждёт изменений всех модулей. Команды оболочки обязаны соблюдать договоры областей; это не изоляция процессов ОС. Пользователь может отвечать на консультации без блокировки всей команды.

Панель над полем сообщения показывает имя, текущую задачу, работу / ожидание / блокер и конкретного коллегу, от которого зависит продолжение. «План задач» раскрывает последовательность и результаты. Нажатие карточки открывает настоящий чат агента; по иерархии чатов можно вернуться к координатору. Статусы основаны на инструментах и штатных задачах DSH.

Перезапуск
Чаты, роли, задания, решения и свидетельства сохраняются. Незавершённый запуск после перезапуска службы получает paused: напишите «Продолжи», координатор вызовет gvs_resume и возобновит работу прежних агентов после проверки частичных результатов. Прерванная задача не считается завершённой. «Останови команду» вызывает gvs_pause. Автозапуск Harness настраивается отдельно.

Дизайн и код
При редизайне дизайнер рассматривает три содержательно разных композиции и согласует направление с Пользователем. Требуются характер продукта, иерархия, пропорции, ритм, типографика, полезные состояния и законченный сценарий. Случайный декор не считается улучшением. Учитываются существующая дизайн-система и ограничения проекта.
Разработчик сохраняет стек, переиспользует компоненты, избегает лишних зависимостей, дублирования состояния и абстракций без задачи. Независимый проверяющий лично изучает код и запускает реальные команды; приёмка требует простоты и соблюдения границ изменений.

2D и 3D
Гейм-дизайнер оценивает расположение объектов, видимость целей/опасностей, управление и обратную связь. Отдельный игровой QA проверяет реальные столкновения, землю, overlap, высокую скорость, триггеры, победу/проигрыш/рестарт, ввод и для 3D камеру. Скриншоты подтверждают внешний вид; физику — действия и наблюдаемое состояние реальной симуляции.
Для Canvas/WebGL тестовая сборка может открыть:
window.__gvsGame = {version:1, engine:'название движка', reset(scenario), step(frames), state()}
state() возвращает JSON с числовым tick; step вызывает production update/physics и рендер, reset задаёт реальные начальные условия. Bridge включается только в тестовой/debug-сборке, например при gvs_test=1. Подменённая физика и готовые состояния недопустимы.
gvs_game_check выполняет reset/step/hold/press/pointer и assert над state. Возвращает настоящие кадры и покрытие collision/gameplay/controls/camera. За вызов 1–32 действия, до 600 кадров на шаг; pointer использует доли viewport 0..1. Размеры: desktop 1280×800, mobile 390×844 по плану.

Для другого движка gvs_native_game_check запускает существующий тестовый runner проекта в foreground. Последняя строка stdout:
GVS_GAME_RESULT: {"schema":"gvs.game/1","engine":"реальный движок","cases":[{"name":"стена","category":"collision","passed":true,"actual":2.75,"expected":2.75}],"screenshots":[{"path":"artifacts/scene.png","viewport":"desktop"}]}
Каждый case содержит фактическое и ожидаемое значение. Скриншоты создаёт сам движок внутри проекта. Код адаптера проверяет другой verify-агент: игровой QA и code reviewer должны быть разными агентами. Без доступного runtime/рендера недостающая часть приёмки остаётся blocked. Unity/Godot/Unreal здесь не установлены и их редакторы не проверялись; для конкретной игры нужен адаптер её движка.

Локальный preview и браузер
Координатор запускает существующую команду проекта через gvs_preview как штатную фоновую задачу. Сервер переживает смену исполнителей; stop ожидает завершения. Preview временный и после перезапуска DSH сам не восстанавливается.
gvs_browser_check открывает настоящий UI на 1440×960 и 390×844, выполняет до 12 семантических действий/проверок, возвращает изображения, ошибки JS и переполнение. Действия: click/fill/select/press/check/scroll/assertText/assertVisible/assertState. Цели — наблюдённые role+name, label или testId.
На этом компьютере используются установленный playwright-core runtime Codex и Microsoft Edge. Изолированный захват локального проекта включает программный ANGLE/SwiftShader для сервисной Windows-сессии без GPU; скорость не характеризует производительность игры на видеокарте. Потеря canvas-контекста фиксируется как ошибка. Личный профиль браузера не используется, внешние ресурсы блокируются. При переносе нужны browserModule/browserExecutable и доступный браузер; автоматической установки движков нет.
Параметры рендера: https://github.com/chromium/chromium/blob/main/docs/gpu/swiftshader.md

Приёмка
verified требует завершённый план без блокеров; независимый успешный code review с фактическими командами; приёмку Пользователем; для UI/игры свежие изображения, действия с проверяемым результатом и отдельный rendered design review. Проверяется фактическая передача изображений рецензенту. Игра дополнительно требует текущих механических свидетельств нужных категорий и проверки адаптера. После изменений старые свидетельства не заменяют свежие. Без обязательных данных получается needs-review.
Это подтверждает перечисленные проверки, а не отсутствие любых ошибок или одинаковый вкус разных моделей. Результат зависит от выбранной модели, задания и проекта.

Данные
В проекте: .gvs/team-<sessionId>.json — команда этого чата; .gvs/<runId>/state.json — запуск; .gvs/latest.json — последний записанный запуск проекта. Чаты/задачи и изображения сохраняет штатный DSH. gvs_status читает состояние после перезапуска. Не редактируйте .gvs вручную во время работы команды.

Установка
Установите @makame/dsh-gvs через Plugin Manager или dsh plugin --profile web add @makame/dsh-gvs. Полная инструкция — README.md. Стандартные режимы сохраняются, из внутренних ролей отдельный режим не создаётся.
Самостоятельная реализация идеи https://github.com/slee-persis/GVS5H; исходный код проекта не копировался. Не официальный плагин DeepSeek.

История автоматически сжимается до переполнения: порог 60%, сохранение последних 12000 токенов, обрезка больших старых результатов инструментов и до двух попыток восстановления overflow. /compact запускает штатное сжатие вручную в свободном чате. Статусы GVS передают компактные сводки, полные свидетельства остаются в .gvs и чатах агентов.


Условный анализ по задаче (2.1)
В начальном брифе Пользователь обязан задать план через gvs_analysis plan. Для простых задач допустим пустой список с объяснением. Для плавности выбирается motion/rendered-sequence, для производительности и других свойств — измерение реального runtime. Выбор определяется целью человека и проектом; слова про плавность служат подсказкой, текстовое переименование можно обоснованно исключить.
Реальный runner запускается независимым verify-агентом через gvs_analysis check и печатает финальный GVS_ANALYSIS_RESULT: JSON gvs.analysis/1. Формат и пример — README.md публичного пакета. Для движения требуются измерения rendered-pixels и frame-timing, минимум 8 фактических PNG/JPEG кадров и 30 измерений пиксельного показателя/времени кадров каждого нужного viewport за минимум секунду. Одни координаты, счётчики тестов и пара снимков не принимаются. Максимум 120 кадров/64 MiB за отчёт. Материалы остаются в проекте, представительные кадры прикладываются рецензентам.
Другой проверяющий изучает исходник анализатора и подтверждает adapterReviewed вместе с ID analysisReports. Пользователь и дизайнер принимают только реально полученные свежие отчёты, указывают их ID и честно описывают ограничения. При смене плана или кода нужны свежие свидетельства. Если рендер/измерение недоступны — анализ остаётся blocked. Пороговые значения определяются задачей; наличие кадрирования само по себе не доказывает отсутствие всех дефектов.

В 2.2.5 статический аудит исходников назначается координатором как reviewFocus:source только для kind:review/scope:increment/analysisIds:[]. Он требует реальных проверок кода и не заменяет визуальную или финальную приёмку.

В 2.2.6 QA разрешена запись собственных отчётов в явно выделенных областях артефактов. Повторные команды к уже продвинувшейся задаче не создают дубли; сбои анализатора показывают фактическую причину, не снимая приёмочные проверки.

В 2.4.2 проверка исходников также распознаёт нестандартный Cargo target-каталог по настоящей сигнатуре CACHEDIR.TAG и .rustc_info.json. Его бинарные результаты не считаются исходниками; похожие по имени папки без маркеров остаются под проверкой. Лимит и fail-closed обработка реальных входов сохраняются.
